RabbitLock is **one credential policy, approval and receipt layer for every coding agent**. Today it enforces the policy with its own local proxy. The roadmap applies the same policy through each agent platform's built-in credential features, evidence a security team can rely on, and the engineering needed for 1.0.

Planned items have no dates. They ship in the order below, and the [changelog](/changelog) records what actually shipped.

## Available today (0.4.x)

- One policy file: per-key host allowlists and approval rules (`never`, `once`, `every`)
- RabbitLock's own proxy for any agent on macOS and Linux; Claude Code's sandbox configured automatically
- Approval dialogs, and a receipt of every use, without values
- Encrypted storage (post-quantum hybrid SOPS), on your machine or shared with teammates through git; optional passphrase
- Agent-led setup, generated secrets the agent never sees, `.env` import

## 1. Check which platforms can be driven (done, 2026-11-24)

We checked 17 agent platforms' built-in credential features against vendor documentation, and tested Claude Code and Codex by hand. Results: [integration matrix](/reference/integration-matrix).

- Five platforms can be configured end to end from a file or an API, secret and hosts: Claude Code CLI, Codex CLI, Claude Managed Agents, the OpenAI Agents API and Daytona. Adapters go ahead.
- None records each use of a credential or lets an outside approver hold one. Through a platform's built-in feature, RabbitLock can apply one policy and detect drift. Per-use approvals and receipts need RabbitLock's own proxy.
- Claude Code on the web and Codex cloud are configured only in their UIs, and Copilot, Cursor and Devin give the agent the real value.

## 2. Policy v2 and platform adapters

- Rules per HTTP method and path, not just per host.
- `rabbitlock plan` and `rabbitlock apply` configure a platform's built-in credential feature from your policy. First: Claude Code CLI, Codex CLI and Claude Managed Agents. Next: Daytona, the OpenAI Agents API and Docker Sandboxes.
- `rabbitlock check` reports where a platform's configuration has drifted from the policy.
- RabbitLock's own proxy stays the fallback wherever a platform has no built-in feature.

## 3. Verifiable receipts

- One receipt format across the proxy and every adapter. For platforms that don't log each use, adapters record what was configured, where and when.
- Receipts are hash-chained and signed. `rabbitlock receipts verify` detects edits, deletions and reordering.
- Export to OpenTelemetry and OCSF for security tools.

## 4. Approvals beyond the desktop dialog

- Terminal and webhook/Slack approvals, with timeouts that deny by default.
- Approvals on platforms that expose a hook for them. Today those hooks approve a tool call or a new host, not a single use of a key.

## 5. Proxy hardening

- **Responses:** secrets that an allowed API echoes back are scrubbed.
- **Protocols:** HTTP/2 and WebSocket support.
- **Local CA:** limited to the hosts in your policy.
- **Short-lived credentials** issued per request, where the provider supports it.
- **Other secret sources:** keys from 1Password, HashiCorp Vault and AWS Secrets Manager.
- **CI:** decrypts through your cloud KMS with OIDC, so no RabbitLock server ever holds keys.
- **Self-hosted sandboxes:** the proxy runs as an egress gateway.

## 6. 1.0

- An external security audit, and fuzzing of every parser.
- Releases published with npm provenance from CI, signed tags and an SBOM.
- Tests on Node 20, 22 and 24, on macOS and Linux, and against real agent CLIs.
- Stored formats frozen, with a deprecation policy and migration commands.
- `rabbitlock doctor`, and a key backup and recovery story.

## Later: team and enterprise

- Receipts collected across a team.
- Signed organization policy distributed to developers and CI.
- Revoking access mid-session.
- SSO.

Your keys stay in your own store or KMS. There is no hosted secrets workspace.
