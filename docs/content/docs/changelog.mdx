## 0.4.2 (2026-11-24)

- New positioning: RabbitLock is one credential policy, approval and receipt layer for every coding agent. The CLI's help text and package description say so. No behaviour changes.
- Public [roadmap](/roadmap).

## 0.4.1 (2026-11-24)

- **The local CA private key is encrypted at rest**, under a key derived from your identity (HKDF-SHA256, then AES-256-GCM). With `rabbitlock key protect`, the one passphrase now covers both keys, with no extra prompt. A plain-text key from an earlier version is encrypted on your next `rabbitlock run`.
- `rabbitlock ca`, `ca trust` and `ca untrust` no longer need the private key.
- With a passphrase-protected identity, `rabbitlock init` doesn't prompt; the CA is created on the first `rabbitlock run`.

## 0.4.0 (2026-11-24)

- **Individual mode by default.** `rabbitlock init` writes a `project` id. Encrypted secrets and receipts live in `~/.rabbitlock/projects/<project>/`, outside the repo, so there's nothing to gitignore and nothing to decide about committing. Existing policies keep working unchanged.
- **Team mode:** `rabbitlock team enable | add | remove | ls` replaces hand-editing `recipients`. Recipients can be named (`{ name, key }`). `remove` lists the secrets to rotate.
- `rabbitlock key` prints your public key.
- `rabbitlock status` shows the mode and where secrets are stored.
- **Optional passphrase on your identity:** `rabbitlock key protect | unprotect`. Commands that need your private key ask on your terminal, while `status`, `ls` and `key` don't. `RABBITLOCK_PASSPHRASE` covers automation. See [Protect your key with a passphrase](/concepts/encrypted-storage#protect-your-key-with-a-passphrase).
- Secrets files and receipts are now written owner-only (`0600`), atomically.

## 0.3.0 (2026-11-24)

- Agent-led setup: [rabbitlock.com/agents.md](https://rabbitlock.com/agents.md) and a Claude Code plugin (`/plugin install rabbitlock --marketplace rabbitlock/rabbitlock`). See [Set up with your agent](/guides/agent-setup).
- `rabbitlock status [--json]`: setup state and next steps, and lets an agent check whether it's running under RabbitLock
- `rabbitlock import .env`: encrypt an existing `.env` in one step
- `rabbitlock init --agents-md`: instructions for coding agents in `AGENTS.md`
- `rabbitlock run` warns when a `.env` file next to the policy still holds a brokered secret's real value
- `RABBITLOCK_SANDBOX` in the agent's environment

## 0.2.0 (2026-11-24)

- `rabbitlock set NAME --generate`: creates a random secret and hands it to you (`--reveal`, `--to-command`) or to nobody (`--no-handoff`), so an agent can set up accounts and services with a credential it never sees. See [Let your agent set up accounts](/guides/provisioning).
- `generated` receipts

## 0.1.0 (2026-11-23)

First public release of the `rabbitlock` CLI.

- Placeholders for secrets, swapped in only on outbound HTTPS to per-secret allowed hosts
- Injection into headers (including Basic auth), URLs, and JSON, form and text bodies up to 1 MiB
- Human approvals (`once`, `every`) through OS dialogs
- Receipts in `.rabbitlock/receipts.jsonl`, never containing values
- Agent sandbox by default: `sandbox-exec` on macOS, `bwrap` on Linux, Claude Code's own sandbox for `claude`
- Encrypted secrets in git (SOPS format, hybrid X25519 + ML-KEM-768 recipients), shareable with teammates
- `rabbitlock ca trust` for Go tools on macOS
